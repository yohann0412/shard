# Adversarial review: Experiment A protocol (before running it)

Every way the numbers could come out wrong in the thesis's favour, and what the protocol does about each. The protocol is PLAN.md §5 (v3). The verdict rule was fixed before any data (commit e5c5361): the median across runnable repos of test-phase(isolated N=1) / test-phase(isolated N=4).

| # | Way the speedup could be flattered | Control | Residual risk |
|---|---|---|---|
| 1 | Comparing isolated arms against a baseline whose Playwright wall time includes `webServer` boot and a build | Test phase = first test begin → last test end, measured by the same reporter in every arm; boot reported separately | None for the verdict metric; vs-baseline numbers are context only |
| 2 | Baseline on a slower database (disk, fsync on, other Postgres major) | Baseline runs against a fresh copy of `seed` on the same isolate-managed Postgres (same binary, same RAM directory, same settings) through `isolate run --baseline` | The baseline's app is started by the repo's `webServer` (maybe a dev server) while isolated apps use `app.start`; recorded per repo, and the harness effect baseline@1 / isolated@1 flags repos outside 0.85-1.15 |
| 3 | Warm caches favour later arms | One discarded warm-up per arm; 3 rounds with the order rotated each round; extra rounds when max/min > 1.10 | Page cache and V8 code cache stay warm across arms (all arms are warm, which is the intended comparison) |
| 4 | Build or snapshot savings counted as speedup | Build happens once, untimed, before any arm; the F5 cache effect is its own number; the verdict uses only the test phase | None for the verdict |
| 5 | "N=4" labelled but fewer tests actually ran at once (`fullyParallel: false`, few files) | Reporter records resolved workers, distinct parallel indexes and max concurrent tests; the scheduling ceiling from N=1 per-file durations is reported next to each speedup | A low speedup explained by the ceiling is still reported as the measured number; the ceiling is context, not a correction |
| 6 | Flaky or failing tests finish fast and shorten the isolated arms | `--retries=0` in every arm; each run's per-test outcomes are compared with baseline@1's reference; mismatching runs are flagged and the mismatching tests listed | The protocol v3 says "re-time on the common passing subset"; if the harness only flags instead of re-timing, RESULTS.md says so for each affected repo |
| 7 | A failure caused by load at N=4 disappears when re-run alone | Isolation failure = fails in ≥ 2 of 3 isolated@4 rounds and passes in ≥ 2 of 3 baseline@1 rounds, regardless of the tool's rerun classification; "timeout under load" is its own category | With 3 rounds, a test that fails 1 in 3 is counted as not an isolation failure; its flakiness is reported separately |
| 8 | Background load from subagents or other work during timed runs | Timed runs only with no subagent running; load average recorded at the start of every run; the harness waits for it to drop below 1.0 | This is a shared cloud VM: noisy neighbours are invisible except through `/proc/stat` steal, which is recorded per run |
| 9 | `CI` differences flip repo behaviour between arms | Every arm sets `CI=true` (not `1`: rallly tests `=== "true"`) | None known |
| 10 | Routing silently broken (every worker hits one app), making "isolated" runs actually shared | Per-worker `xact_commit` growth checked after every run; a run with an idle used database is invalid and excluded | Test-side writes to w_i can mask an app that ignores its URL (review of F4); stated in RESULTS.md |
| 11 | Only the easy repos are measured | Every attempted repo is listed with its outcome and reason; the harvest funnel is reported (998 scanned → 96 qualified → 12 scouted → 3 green) | The sample is 1-3 real repos; with fewer than 3, Claim A is reported per repo and labelled inconclusive (PLAN_REVIEW addendum) |
| 12 | The fixture was built to collide and then be fixed, so it flatters Claim A | The fixture is never pooled with real repos; it is reported separately as a mechanism demonstration | None |
| 13 | Oversubscribed N=8 on 4 cores made to look like a plateau caused by something else | N=8 only on the fixture, labelled "oversubscribed"; `lscpu` recorded (4 cores, 1 thread per core) | None |
| 14 | Memory numbers flatter (or scare) | Peak RSS summed over process trees; Postgres shared memory counted once per backend, so it is an upper bound, stated as such | Not PSS; fine as an upper bound |

What the lead will do if a control could not be applied: say so next to the number in RESULTS.md, not in a footnote.
